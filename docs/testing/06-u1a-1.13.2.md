## 1. 改動摘要

### 1.1 為什麼不是「相容層」
1.13 的 Bukkit 已**移除** `ItemStack(int,…)`、`getTypeId`、`setTypeId`、`Material#getMaterial(int)`。沒有 `api-version` 的插件會被伺服器以 legacy 模式重寫位元碼（`Material.X` 會變成 `LEGACY_X`），與新名稱的程式碼互相衝突，所以 **`plugin.yml` 已設 `api-version: 1.13`**。U1a 保留的是「資料」的舊數字 ID:data，不是舊 API。

### 1.2 `compat` 套件（版本差異只在這裡與 `ItemManager`、`nms`）
| 類別 | 作用 |
|---|---|
| `LegacyBridge` | 舊 id:data ⇄ 1.13 `Material`／`BlockData`。用 `Material.values()` 中的 `LEGACY_*` 建 id 表，轉換交給伺服器的 `UnsafeValues#fromLegacy`／`toLegacy`；有快取。方塊反查用 `BlockData` 對照表（同一狀態有多個舊 id 時，取 Bukkit 的標準 id）；水／岩漿依 level 回 8／9、10／11；舊骷髏頭（144）依 data 放骷髏頭或牆上骷髏頭；舊藍圖中無效的 data 位元（例如雙石磚台階）會被丟掉，不會變成空氣 |
| `LegacyMaterials` | 改為 1.13 名稱的語意判斷與設定集合；藥水改看 `PotionMeta`；`willInstantBreak` 從 `CivGlobal` 移入並展開成 1.13 的各種變體 |
| `LegacyIds` | 1.12 名稱已不存在或意義已變的 `Material` 常數，保留當時的數字 ID（例如 `RAW_FISH`=349、`CARROT`=141）。程式碼行為與 1.12 逐字相同 |
| `LegacyBiomes` | 生物群系名稱（culture.yml、`CHUNK_BIOMES` 資料表、農場設定都存 1.12 名稱）⇄ 1.13 `Biome` |
| `LegacyEnchantments` | 附魔數字 ID（`InventorySerializer`、`Blacksmith` 存的）⇄ `Enchantment` |

### 1.3 其他
- `ItemManager`：簽名不變，內部改走 `LegacyBridge`；新增 `getItemMaterial(id,data)`。`getData(ItemStack)` 對工具回傳損耗、其他物品回傳舊「變體 data」。
- `nms/v1_12_R1` 刪除（可由 tag `u0-paper-api` 取回），新增 `nms/v1_13_R2`：`NBTTagCompound#c()`→`getKeys()`；馬的「開啟背包」混淆名稱 `f`→`c`（`c` 有多個同參數數量的多載，改依參數型別 `EntityHuman` 比對）；**`display.Name` 寫入 JSON 文字元件（預設不斜體），`display.Lore` 維持舊式純字串（1.13 的 lore 還不是 JSON，1.14 才改）；讀取同時接受 JSON 與純字串**。2026-10-06 實測：lore 曾誤寫成 JSON，客戶端把整串 JSON 當文字顯示；已改回純字串（`tools/LoreFlowCheck.java` 離線驗證）。
- `InventorySerializer`：序列化格式不變（`t@<id>&d@<data>`），但 `d` 現在存變體 data（舊的 `getDurability` 語意），反序列化用 `createItemStack(id,1,d)` 還原。
- `Template.initAttachableTypes`、`CustomItemManager`、`AdminCommand` 等 9 個檔案的已消失 `Material` 常數改走 `LegacyIds`；`WarRegen`、`ArmorType`、`BlockListener`、`WarListener` 的 switch／比較改 1.13 名稱。
- `CivSettings.previewBlock`：設定的材質名稱不存在時警告並用玻璃，不再是 `null`。
- 新增 `tools/LegacyBridgeCheck.java`（離線檢查，見 §2）。

### 實測紀錄
- 第一次伺服器啟動（2026-10-06 19:00，Paper git-Paper-657 / 1.13.2，使用者提供 `latest.log`）：**CivCraft 啟用失敗**。設定檔、`Generating Trade Goodie/Mob Spawner Locations` 都完成，之後 `LoreCraftableMaterial.buildRecipes`（第 326 行，無序配方）丟出 `IllegalArgumentException: Recipe requires at least one non-air choice!`，插件被停用，後續日誌皆為 `NoClassDefFoundError: CivGlobal` 的連鎖。其餘錯誤（CustomMobs 自行停用、Herochat `NoSuchMethodError`）與基準相同。
- 原因（兩個，離線檢查重現）：① `ItemManager.getMaterialData` 回傳的 `MaterialData` 在 1.13 會把材質轉回 `LEGACY_*`，配方因此全是空氣；② `materials.yml` 的 32 組 `383:<實體 id>`（怪物蛋，data＝實體編號）沒有對照，轉成空氣。
- 修正：配方改直接傳 `Material`（移除 `getMaterialData`、`getData(MaterialData)`、`setData(MaterialData,…)`）；`LegacyBridge` 新增怪物蛋對照（`383:<實體 id>` ⇄ `<ENTITY>_SPAWN_EGG`，內部鍵改為 `id<<8|data`）；`MobSpawnerPopulator`／`TradeGoodPopulator` 的看板方向改讀 `BlockState`。
- `LegacyBridgeCheck` 新增第二個參數：`materials.yml`。655 組 id:data 現在全部轉為真正的物品（先前 32 組為空氣）。
- 第二次啟動（19:09，已部署修正後的 jar，確認不含 `getMaterialData`）：**同一處失敗**（`buildRecipes` 第 326 行）。真正原因是 `materials.yml` 有 4 組 `data: -1`（「任何 data」的萬用字元：`12:-1` 沙、`17:-1` 原木、`162:-1` 原木２、`5:-1` 木板），舊程式把 -1 當 data 15 查，轉成空氣，`mat_compacted_sand` 這類只有萬用字元成分的配方就整個是空氣。第一次的修正是必要的，但不是唯一原因；`LegacyBridgeCheck` 當時沒掃負數，所以沒抓到。
- 修正：`ItemManager.getRecipeChoice(id,data)`；`data -1` 回傳涵蓋舊 id 所有變體的 `RecipeChoice.MaterialChoice`（沙＝沙＋紅沙、`17`＝橡／杉／樺／叢林原木、`162`＝相思／黑橡原木、`5`＝六種木板），其他回傳單一材質；`LegacyBridge.itemMaterial` 對負 data 視為 0。`LegacyBridgeCheck` 現在也掃 `-1`（659 組全部有效）。
- 第三次啟動（19:12，新 jar；堆疊 `buildRecipes:330`，確認是 `-1` 修正後的程式）：**仍是同一個例外**。離線模型（`tools/LegacyRecipeCheck.java`、`LegacyRecipeCheck2.java`，用伺服器的 `cache/patched_1.13.2.jar`，照 `ConfigMaterial` 的解析方式含成分去重、對每個無序配方走 `ShapelessRecipe.addIngredient` → `CraftShapelessRecipe.fromBukkitRecipe` → `CraftRecipe.toNMS`）對 200 個可合成配方全部通過，**與伺服器行為不一致，根因尚未找到**。
- 因此本次改為：`LoreCraftableMaterial.registerRecipe` 包住 `addRecipe`，單一配方被伺服器拒絕時記錄 `Could not register the recipe of '<id>': … ingredients=[…]` 並略過，不再讓整個插件停用。下一次啟動的日誌會直接指出是哪個配方、成分是什麼。
- 第四次啟動（19:20，含記錄用的 jar；伺服器日誌，使用者同時提供的客戶端日誌只顯示 19:02 玩家進入後執行指令得到「internal error」，是插件已停用的結果，沒有額外資訊）：`registerRecipe` 生效，20 個配方被拒絕（`mat_cannon_wheel`、`mat_refined_wart`、`mat_refined_stone_alt0–2`、`mat_carbide_molding`、`mat_metallic_crystal_1–4`、`mat_royal_crown`、`mat_badge_of_leadership`、`mat_steel_sword_blade`、`mat_crafted_sticks`、`mat_refined_sugar`、`mat_vanilla_slime`、`mat_refined_slime`、`mat_crafted_string`、`mat_refined_feathers`、`mat_carbide_steel_sword_hilt`），**所有成分都是 `MaterialChoice{choices=[AIR]}`**；其餘約 180 個（含 `mat_carved_leather` 334、`mat_crafted_reeds` 338、`mat_refined_sulphur` 289、`mat_refined_stone` 1←4、`mat_compacted_sand` 24:1←12:-1）正常註冊。接著 `mat_refined_wood`（成分 `17:-1`）在 `getRecipeChoice` 丟出 `Must have at least one choice`（`itemVariants(17)` 在伺服器上是空的），未被捕捉，插件再次停用。
- 結論：**伺服器上 `LegacyBridge.itemMaterial` 對部分舊 id（1、17、53、280、287、353、372…）回傳 AIR，同樣的呼叫在離線檢查（用同一份 patched jar）回傳正確材質**。原因未明，推測與伺服器端 `CraftLegacy` 的狀態有關。
- 本次改動：① `itemMaterial` 在物品表查不到時，改查方塊表與方塊狀態，並在日誌印出 `legacy item <id>:<data> (<LEGACY_名稱>) has no item mapping; block table=…, block state=…`；② `getRecipeChoice` 在 `-1` 查不到任何變體時不再丟例外（改走單一材質，由 `registerRecipe` 記錄並略過）。
- 第五次啟動（19:28，含診斷的 jar）：插件**走過配方、資料庫、藍圖前的載入（`Done <3`）**，但 ① 83 個配方因成分全為 `AIR` 被略過（比第四次的 20 個多，且包含先前成功的，例如 `mat_refined_sulphur`），**日誌沒有任何 `has no item mapping`**，表示不是 `fromLegacy` 回傳 AIR，而是 `legacyMaterial(id)==null` 的靜默路徑，或另有狀態相依；② `ACManager.init` 丟出 `Channel must contain : separator (attempted to use CAC)`（1.13 的外掛頻道必須是 `namespace:name`），插件再次停用。
- 本次改動：`ACManager.init` 註冊頻道失敗時警告並設 `enabled=false`（`PlayerLoginAsyncTask`、`WarAntiCheat` 都以 `isEnabled()` 判斷，ROADMAP §6 本來就要在 U1 前移除 Anti-Cheat）；`/dbg packet` 在停用時回報錯誤；`legacyMaterial(id)==null` 時也會在日誌印 `legacy item id N is unknown`；啟動時（`Nms.init` 之後）印出 `LegacyBridge: N old ids known` 與 11 個常用舊 id（1、4、5、12、17、53、280、287、334、353、372）的轉換結果。
- 第六次啟動（19:32）：**CivCraft 成功啟用**（`Done (4.477s)`，沒有 `Disabling CivCraft`；`CivCraftAC is disabled` 警告如預期）。但 `LegacyBridge: 0 old ids known`：**伺服器上 `LegacyBridge` 的靜態初始化沒有找到任何 `LEGACY_*` 材質**（`Material.values()` 路徑得到 0 筆），因此所有舊 id 都轉成 AIR（這就是配方成分全為 AIR 的原因，也解釋了第四、五次結果不同：每次被記錄的 id 不同）。離線檢查找不到這個差異，因為離線環境的 `Material.values()` 含有 `LEGACY_*`。
- 本次改動：靜態初始化除了 `values()`，另以反射讀取 `Material` 的所有 `LEGACY_*` 靜態欄位補表，並把兩條路徑各找到幾筆印在啟動日誌（`LegacyBridge: N old ids known (Material.values()=…, legacy via values()=…, added via fields=…)`）。
- 第七次啟動（19:37）：`LegacyBridge.selfTest` 在 id 280（木棍）丟 NPE（`CraftLegacy.fromLegacyData`），插件停用。修正見 §1.4。

- 往返不同的 22 組 id：`STATIONARY_WATER`／`STATIONARY_LAVA` 帶有非 0 的 level（9:1–12、11:2–14，原版不會有的藍圖資料，讀回為流動的 8／10）、`DEAD_BUSH` 32:0（與 31:0 同一狀態）、`DOUBLE_STONE_SLAB2` 181:1／4（無效 data）。data 不同的 54 組：空氣的 data、樹葉的 decay／persistent 位元、箱子與終界箱的朝向（`dataOf` 對不到精確狀態時，執行期會改用 `Block#getData()`）、盆栽（種類在 tile entity）。**全部屬於 1.13 不再區分的舊位元，不是轉換錯誤**，但結構驗證若拿讀回的 data 與藍圖比對，這些方塊可能被判為不同（待伺服器驗證）。
- 「同名不同意義」的 `Material` 常數稽核（原始碼用到的 188 個名稱，比對 1.12 的 `getId()` 與 `LegacyBridge.idOf`）：`CARROT`／`POTATO`／`FLOWER_POT`（方塊→物品）、`WHEAT`、`SUGAR_CANE`、`MAP`、`SIGN`、`IRON_DOOR`、`CAKE`、`GRASS`、`DEAD_BUSH`。有用到的已改走 `LegacyIds` 或 1.13 名稱；沒有用到的不處理。
